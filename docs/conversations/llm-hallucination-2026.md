## 🤖 ChatGPT

我觉得你的观察很有意思：**2026 年，LLM 幻觉问题并没有消失，但它已经不像 2023 年那样，是整个行业最显眼的问题了。**

这背后其实有一个很重要的变化：

早期大家关注的是：

> 大模型为什么会一本正经地胡说八道？

现在越来越多的关注点变成了：

> 如何让大模型在一个真实业务系统中，可靠地完成任务？

这两者有联系，但不是同一个问题。

尤其是在 Agent、企业知识库、代码助手这些场景里，LLM 的可靠性已经不再只是模型自身的一个指标，而是整个系统的工程问题。

不过，不能因为大家谈论得少了，就认为幻觉已经被解决。我们需要区分几个层面。

## 1. 幻觉确实减少了，但不是所有类型都减少

我认为需要把幻觉分成三类：

| 幻觉类型 | 2026 年的情况 |
|---|---|
| 常识性错误 | 大幅改善，很多过去容易出错的问题现在可以正确回答 |
| 复杂推理错误 | 仍然存在，特别是数学、长链推理、复杂约束 |
| 无依据的事实编造 | 仍然是核心问题，模型可能对不知道的事情给出确定答案 |

尤其是第三类。

比如，你问模型：

“某个开源项目的 Agent 身份管理机制是怎样的？”

模型可能给出一个架构非常合理的答案，甚至包含接口、配置项、源码文件路径。

但其中某个接口可能根本不存在。

这种幻觉，比过去的常识性错误更难识别，因为它的答案看起来更专业。

2026 年 4 月，《Nature》发表了一篇研究，专门分析为什么幻觉至今仍然存在。研究认为，标准的准确率评价会鼓励模型猜答案，而不是在不确定时拒绝回答。<Cite refs={["turn742261search0"]}/>

这其实是一个很重要的结论：**模型答得多，不等于模型答得可靠。**

    斯坦福 2026 AI Index 报告引用的 HHEM 文档摘要评测中，15 个模型的幻觉率在这个区间内。<Cite refs={["turn742261search9"]}/>

    <title size="2xl">22%–94%</title>

  </box>

这两个数字不能直接比较，因为任务和指标不同。

但它们说明一个事实：

**在有明确参考文档的任务里，模型可以表现得非常可靠；在没有明确证据、需要自行回忆事实的任务里，可靠性仍然可能大幅下降。**

所以，网上说某个模型幻觉率只有 3%，并不意味着它在所有业务场景中只有 3% 的错误。

## 3. 为什么感觉行业已经不怎么讨论幻觉了？

我认为主要有四个原因。

### 原因一：模型能力的提升掩盖了幻觉

模型的整体能力进步很快。

以前一个模型可能连复杂的 Java 代码都写不出来，现在它能够完成整个模块的实现。

在这个过程中，用户的注意力自然从“模型能不能回答”转向了“模型能不能可靠地完成工作”。

### 原因二：RAG 和工具调用改变了问题的处理方式

这是我认为最重要的工程变化。

以前：

```text
用户提问
   ↓
LLM 根据参数记忆生成答案
   ↓
返回答案
```

现在：

```text
用户提问
   ↓
检索知识库 / 查询数据库 / 调用工具
   ↓
获取真实证据
   ↓
LLM 基于证据组织答案
   ↓
校验结果
   ↓
返回答案
```

例如，企业内部的 Agent 不需要让 LLM 记住数据库的真实状态。

它可以直接查询数据库。

不需要让 LLM 记住代码仓库里的真实实现。

它可以使用代码搜索、LSP、AST 分析等工具获取证据。

这就把一部分幻觉问题转化成了系统设计问题。

当然，RAG 并不能保证模型正确理解检索结果，工具调用也可能出现错误。

### 原因三：Agent 的可靠性不再单纯依赖 LLM

比如你正在考虑的运维 Agent。

如果 Agent 要回答：

“为什么这个业务页面报错了？”

它可以：

- 检索历史故障知识。
- 查询日志。
- 查询数据库。
- 分析代码。
- 执行验证。

这些能力使它不必完全依靠模型内部的知识。

但也会引入新的风险：工具选错、参数错误、证据解释错误、执行结果被误读。

换句话说：

**幻觉没有简单地消失，而是从单纯的文本生成问题，扩展成了整个 Agent 系统的可靠性问题。**

### 原因四：行业开始把重点放在可验证性上

这点尤其值得关注。

2026 年的研究依然在专门研究幻觉检测。

例如 ACL 2026 的 PROBE 研究，将幻觉检测拆成四个步骤：

1. 将答案拆成独立事实声明。
2. 查找对应证据。
3. 判断证据是否支持声明。
4. 定位具体的幻觉内容。

研究发现，即使给模型提供真实答案作为参考，当前模型在幻觉检测上仍然存在明显不足，尤其是证据查找环节。<Cite refs={["turn742261search6"]}/>

这意味着我们不能简单地用另一个 LLM 问一句“你刚才有没有产生幻觉？”就认为完成了校验。

## 4. 对企业 Agent 来说，真正值得关注的是什么？

我觉得可以把问题进一步拆成三个层次。

<box border radius="xl" gap={3} padding={3}>
  <box gap={1}>
    <badge color="secondary">第一层</badge>
    **模型是否知道自己不知道？**

    这是模型自身的事实可靠性与不确定性表达能力。
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <badge color="secondary">第二层</badge>
    **系统能否提供可信证据？**

    这是 RAG、工具调用、数据库查询、代码分析等能力。
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <badge color="secondary">第三层</badge>
    **系统能否验证最终结果？**

    这是测试用例、规则校验、执行结果验证、人工审批与审计。
  </box>
</box>

举个具体例子。

运维 Agent 判断一个页面报错是因为数据库连接池耗尽。

它不能仅仅因为 LLM 说“连接池耗尽”就认定故障原因成立。

它应该能够找到：

- 发生错误的时间。
- 对应的日志。
- 连接池使用率。
- 数据库连接异常。
- 相关代码路径。

然后判断这些证据是否支持结论。

如果证据不足，它应该说：

“目前怀疑连接池耗尽，但尚未找到足够证据确认。”

这才是一个可靠的运维 Agent 应该具备的行为。

## 5. 我的最终判断

我会这样概括 2026 年的 LLM 幻觉问题：

**对于普通用户的日常问答，幻觉已经不再像早期那样突出；对于需要事实准确性、可追溯性和执行可靠性的企业系统，幻觉仍然是一个没有被根本解决的问题。**

而且有一个反直觉的地方：

模型越强，越能够生成专业、流畅、完整的错误答案。

这会让一些幻觉更难被人类发现。

所以，未来企业 AI 系统的竞争力，不一定取决于谁使用了最强的模型，而可能取决于：

- 谁能给模型提供更好的证据。
- 谁能限制模型的权限和行动范围。
- 谁能更有效地验证模型的结果。
- 谁能通过持续评测发现系统的失效模式。

这也解释了为什么 Agent 评测平台、Guard、AI Gateway、工具权限控制和执行结果验证这些基础设施，仍然很值得投入。

幻觉问题从“模型为什么胡说八道”，正在逐渐变成“我们如何构建一个即使模型会犯错，也能可靠运行的系统”。

## 🤖 ChatGPT

你说的这个方向很关键。Datadog 把 LLM-as-a-judge 放到生产流量中实时运行，实际上是在把我们刚才讨论的“幻觉检测”，从离线模型评测推进到在线生产观测。

这和传统的 LLM 测试有很大区别：

- 离线评测：提前准备一批测试用例，判断模型是否可靠。
- 在线评测：真实用户每次请求都可能成为评测样本。
- 黑盒评测：不需要知道模型内部参数、推理过程或训练数据，只判断输入、输出和上下文是否符合要求。

| 能力 | Custom LLM-as-a-Judge | AI Guard |

| 是否阻塞用户请求 | 通常不阻塞 | 可以同步阻塞 |
| 典型用途 | 幻觉、事实性、回答质量 | Prompt Injection、危险工具调用 |

如果是质量评测，通常可以异步执行。

如果是安全拦截，则必须在危险操作发生之前完成判断。

## 我觉得 Datadog 这套东西最有价值的地方

不是简单地让另一个 LLM 检查当前 LLM。

而是建立一个闭环：

```text
真实生产请求
      ↓
Agent 执行
      ↓
记录完整 Trace
      ↓
在线 Judge 评测
      ↓
发现失败样本
      ↓
人工复核 / 自动归类
      ↓
进入评测数据集
      ↓
优化模型 / Prompt / RAG / 工具
      ↓
离线回归测试
      ↓
重新部署
```

Datadog 还支持把生产中发现的问题 Trace 导入评测数据集，让生产问题直接成为后续改进的依据。<Cite refs={["turn216606search6","turn216606search2"]}/>

这就把我们之前讨论的 Agent 评测系统、生产观测和持续迭代真正连接起来了。

**我的判断是：LLM 幻觉检测正在从一个模型研究问题，演变成一个生产系统的持续质量监控问题。**

而 Datadog 这种架构值得借鉴的核心，是把 Judge 的结果和生产请求关联起来，并且让这些结果能够触发后续动作，而不是仅仅展示一个评测分数。
