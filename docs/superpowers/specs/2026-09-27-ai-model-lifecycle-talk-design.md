# 《从数据到生产：AI 模型的完整生命周期》分享设计

> 2026-09-27 · 时长约 60-65 分钟（含问答弹性）· 结构：方案 A 修订版（一条流水线走两遍，重心 Agent）

## 1. 目标与听众

- **听众**：普通开发工程师 + 算法同事（小公司；算法同事也未必接触过业界先进的模型生产流程）
- **定位**：重生命周期与工程流程，轻算法数学细节——不放公式，讲「是什么、怎么运转、业界怎么做」
- **成功标准**：
  - 开发同学带走一张完整的 AI 工程流程地图，今后参与 AI 项目知道自己在哪一环
  - 算法同学带走业界先进实践的具体锚点（Google/Uber/Meta/Anthropic/LinkedIn 的真实做法与数字）
  - 所有关键论断有来源可查，无编造

## 2. 总体叙事

**一条流水线，走两遍。** 先完整走一遍传统 ML 的生命周期闭环，再在 LLM 时代把同一条流水线重走一遍（重心落在 Agent 与生产迭代），最后用统一框架收束「什么变了、什么没变」。贯穿全场的问题：**一个 AI 能力究竟是如何从数据逐步走向生产并持续迭代的？**

## 3. 分节设计

### 第 0 节 开场（5'）

- **开场提问（钩子）**：「做一个 AI 功能，写模型/调模型的工作量占百分之多少？」→ 揭底：行业经验法则是**数据准备约占项目的 80%**（常被称为 data munging，其中清洗往往是最耗时任务）【单源：CRISP-DM 官方介绍 datascience-pm.com】
- **全景图**：放出本场「生命周期地图」——数据→训练→评测→部署→监控→反馈，两个时代共用这条主线
- **两个承诺**：①一套框架看懂传统 ML 和 LLM 应用；②全部引用业界真实做法，不讲玄学

### 第 1 节 传统 ML 生命周期闭环（20'）

**1.1 标准流程是什么（4'）**
- Google 定义的 8 步：数据抽取 → 数据分析 → 数据准备（清洗/划分/特征工程）→ 模型训练 → 模型评估 → 模型验证 → 模型服务 → 模型监控；**这些步骤的自动化程度 = 你的 MLOps 成熟度**【已验证 3-0：Google Cloud Architecture Center】
- CRISP-DM 六阶段（业务理解→数据理解→数据准备→建模→评估→部署）：1999 年发布，KDnuggets 2002/2004/2007/2014 四次投票均为使用率第一；**阶段顺序不是刚性的，来回迭代是常态**【单源：datascience-pm.com】
- 关键局限：CRISP-DM 的部署阶段包含「制定监控与维护计划」，但**没有定义项目结束后的运营工作**——这正是后来 MLOps 补上的空白【单源：datascience-pm.com】

**1.2 数据环节（4'）**
- 采集 → 清洗 → 标注 → 数据集划分 → 特征工程；80% 精力在数据（呼应开场）
- 标注质量与成本：标注是传统 ML 的「人工飞轮入口」
- 特征的平台化：Uber Michelangelo 自 2016 年起建设集中式 Feature Store，**约 10,000 个特征跨团队共享、每日自动计算更新**（ Feast 等开源特征平台的前身）【单源·一手：Uber Engineering 2017】

**1.3 训练与实验管理（3'）**
- 实验跟踪/评测/模型注册/部署是四大基础能力【已验证 3-0：mlflow.org】——MLflow 是事实标准之一（月下载 3000 万+，Apache 2.0，Linux 基金会项目）
- 模型选择：离线指标（交叉验证、holdout）+ 偏差分析
- 时代注脚：Michelangelo 时代的主力模型是 XGBoost/GBDT（如 UberEATS 送餐时长预测），不是深度学习【单源·一手：Uber 2017】

**1.4 部署上线（3'）**
- 上线形态：实时推理服务（Michelangelo 最高流量模型 **25 万+ QPS，P95 <10ms**）【单源·一手：Uber 2017】
- 上线策略三件套：**影子部署**（新模型只记录不生效）、**金丝雀**、**A/B 测试**——Evidently 把这三种列为需要监控的三类场景【单源：Evidently AI 课程】；CRISP-ML(Q) 把 A/B 与 canary/blue-green 列为标准部署任务，并要求有回退预案【单源：ml-ops.org】

**1.5 监控与漂移（4'）**
- 模型会衰变，**不止因为代码缺陷，更因为数据分布在变**【已验证 3-0：Google】
- 两类漂移：**数据漂移**（输入分布变化）vs **概念漂移**（输入与目标的关系变化，可渐变可突变）【单源：Evidently】
- 生产故障分类学：多数故障源于**数据质量与完整性**（管道断裂、上游 schema 变更、数据丢失），另有训练-服务偏差（training-serving skew）、级联模型的上游故障、弱势子段表现差等【单源：Evidently】
- 标签延迟问题：真实标签不会立刻回来 → 用**代理指标**（预测分布漂移、输入漂移、新类别占比）做预警【单源：Evidently】
- Michelangelo 的落地实现：自动抽样记录线上预测 → 与后续回流的真实结果 join → 生成线上准确率时序指标 + 阈值告警【单源·一手：Uber 2017】

**1.6 反馈闭环与成熟度（2'）**
- 闭环的本质：**线上数据反哺下一轮训练**。Google 定义 CT（持续训练）为 ML 系统特有：CI 不只测代码还要测数据/模型，CD 部署的是「训练流水线」，CT 自动重训并上线【已验证 3-0：Google】
- 成熟度阶梯：
  - Google 三级：L0 全手动 → L1 ML 流水线自动化（+CT）→ L2 再加 CI/CD【已验证 3-0】
  - 微软五级：L0 无 MLOps（全手工、无集中追踪）→ L2 训练自动化+特征平台 → L3 部署自动化（CI/CD 全链路可追溯+A/B 集成）→ L4 漂移信号自动触发重训【已验证 3-0：Microsoft Learn】
  - 给听众的定位工具：「我们公司在哪一级？」
- **本节小结**：闭环 = 采集→训练→评测→部署→监控→反哺。这张地图 LLM 时代依然成立，只是每个环节的形态都变了。

### 第 2 节 LLM 时代：走向 Agent（20'）

**2.0 模型底座（3'，一句话背景，不讲 DL/Transformer 历史）**
- 「模型从哪来」一页纸：**预训练**（海量文本上的下一词预测，学会语言与世界知识）+ **后训练**（SFT 指令微调 + 偏好对齐，学会「听话」）——Llama 3 报告明确将基础模型开发生命周期定义为这两阶段【单源·一手：arXiv 2407.21783】
- 两个数字感受量级：Llama 3 预训练数据 **15T tokens**（Llama 2 是 1.8T）；405B 模型用 16K 张 H100、约 **50 倍于 Llama 2 的算力**【单源·一手：Llama 3 / Meta 工程博客】
- Chinchilla 定律：算力最优要求**参数量与数据量同比例增长**，此前多数大模型「训练不足」【单源·一手：arXiv 2203.15556】
- 为什么对齐重要：InstructGPT 证明 **1.3B 参数对齐模型的人类偏好度超过 175B 原始 GPT-3（参数少 100 倍）**——对齐的价值大于堆参数【单源·一手：arXiv 2203.02155】
- 小公司视角：底座要么调 API 要么用开源，**我们不造底座，重心在应用层**——引出下文

**2.1 RAG 精要（5'）——Agent 的一项核心「知识能力」**
- 完整 pipeline：切片 → embedding → 检索 → 重排 → 生成
- 生产级参数起点【单源：StackAI 企业实践】：
  - 切片：256 / 512 / 1024 tokens 实验，重叠 10-20%；参考默认 chunk 512 / overlap 15%
  - 两段式检索：先粗召回 50-200 条（向量+BM25），再重排出 5-12 条进上下文；参考默认 vector 100 + BM25 100 → 融合 → 重排 → 最终 8 条
  - **混合检索常是效果最大的一次跃迁**（向量检索丢精确匹配：型号、错误码、ID，BM25 补上），RRF 融合
  - Cross-encoder 重排是「很多 RAG 系统达到生产级」的那一步
- RAG 的迭代也走生命周期：金标集（50-200 条真实用户查询）+ 检索指标（Recall@K / MRR / nDCG）+ 忠实度/引用覆盖率【单源：StackAI】——为第 3 节埋线

**2.2 Agent 重点（12'）**
- **定义先行**（Anthropic 的区分）：**workflow** = LLM+工具按预定义代码路径编排；**agent** = LLM 动态决定自己的流程与工具使用；统称 agentic system【单源·一手：Anthropic Engineering】
- 基础积木：**增强型 LLM** = LLM + 检索 + 工具 + 记忆
- **五种生产模式**（Anthropic 从数十个团队的生产实践中总结）：prompt chaining / routing / parallelization（分段与投票变体）/ orchestrator-workers / evaluator-optimizer；自主 agent = LLM 基于环境反馈循环使用工具【单源·一手：Anthropic】
- **ReAct 范式**：推理与行动交织——推理轨迹帮助制定/更新计划与处理异常，行动对接外部知识源；在 HotpotQA/FEVER 上缓解纯思维链的幻觉与错误传播；可解释性更强【单源·一手：arXiv 2210.03629】
- **工具接入标准化：MCP**——开放标准，「AI 应用的 USB-C」；client-server 架构（host 为每个 server 建一个 client）；三种原语：Tools（可执行函数）/ Resources（上下文数据）/ Prompts（模板）；JSON-RPC 2.0 + STDIO/Streamable HTTP 两种传输【单源·一手：modelcontextprotocol.io】
- **工具设计 = ACI**：Anthropic 造 SWE-bench agent 时**花在工具定义上的精力超过 prompt 本身**；agent-computer interface 值得投入与人机界面同等的严谨度【单源·一手：Anthropic】
- **多智能体**：orchestrator-worker 模式（主 agent 规划+派生 3-5 个并行子 agent+汇总引用）；Anthropic 内部评测多智能体系统**超过单 agent 90.2%**，复杂查询研究时间最多降 90%【单源·一手：Anthropic】
- **成本账（必讲）**：token 用量单独解释了 80% 的性能方差；生产数据中 **agent 约花 4 倍于对话的 token，多智能体约 15 倍**——多智能体只对高价值任务划算【单源·一手：Anthropic】
- **工程忠告**：最成功的实现用**简单、可组合的模式**而非复杂框架；建议从直接调 API 起步；自主 agent 上线前要沙箱测试+护栏（成本与误差复利）【单源·一手：Anthropic】

### 第 3 节 生产与持续迭代（15'）

**3.1 推理服务速览（3'）**
- 瓶颈在显存：KV cache 单序列可达 1.7GB（LLaMA-13B），传统推理系统因碎片化与过度预留**浪费 60-80% 显存**【单源·一手：vLLM 博客】
- vLLM 的 PagedAttention：借鉴操作系统虚拟内存分页，显存浪费 <4%；吞吐最高 **24× 于 HF Transformers、3.5× 于 TGI**；LMSYS Chatbot Arena 用后 GPU 减半（日均 3 万请求、峰值 6 万）【单源·一手：vLLM】
- 量化：用精度换显存，让大模型跑在更多设备上；FP8/INT8/INT4、GPTQ、AWQ 等格式与硬件代际强相关（FP8 需 Ada/Hopper）；KV cache 也可单独量化【单源·一手：vLLM 文档】
- 投机解码实战：LinkedIn 在 vLLM 上启用 n-gram 投机解码（无需草稿模型），**同 QPS/SLA 下吞吐近 4×、P90 延迟平均 -66%、输出无损**；其前提是负载特征（生成内容与输入高度重叠）——方法选型要贴合负载【单源·一手：LinkedIn Engineering 2025】

**3.2 监控（4'）**
- 传统服务监控（可用性/延迟）不够，要加**数据健康与模型健康两层**【单源：Evidently】
- LLM 应用监控四维度：**质量（幻觉率/用户反馈）、成本（token）、延迟、trace（轨迹可观测）**；MLflow 已内建 OpenTelemetry tracing、50+ 内置指标与 LLM judge、prompt 管理与 AI Gateway 成本管理【已验证 3-0：mlflow.org】
- 幻觉率的现实：生产中即便有 RAG 与好 prompt，**典型事实性错误率约 5-10%，降到 2% 以下极其困难**【单源：Eugene Yan】
- 实时幻觉检测（Datadog 生产实践）：黑盒 LLM-as-judge（客户多用黑盒模型；扰动式方法要 5-10 倍成本）；把 bad case 自动分类为**「与上下文矛盾」与「无依据论断」**两类，敏感场景两类都拦、不敏感只拦矛盾【单源·一手：Datadog 2025】

**3.3 Bad Case 收集与归因（4'）**
- 收集渠道：显式反馈（点赞点踩、人工接管）+ 隐式信号（用户重试、放弃、改写）
- 评测集不用大：Anthropic 的多智能体系统**从约 20 条真实查询起步**；StackAI 建议 50-200 条真实用户查询做金标集【单源·一手：Anthropic / StackAI】
- 评测方法：单次 LLM-as-judge 调用打 0.0-1.0 分 + rubric 通过/失败，与人工判断最一致；但人工测试仍必要——Anthropic 靠人工发现「agent 偏爱 SEO 内容农场而非权威来源」这类 judge 抓不到的问题【单源·一手：Anthropic】
- 注意 LLM-as-judge 的局限：在幻觉检测上可靠性有限（ChatGPT/Claude 2 区分事实与幻觉摘要仅 53.8-58.5% 准确率）；少量任务数据微调专用检测模型可把 ROC-AUC 从 0.56 提到 0.85【单源：Eugene Yan】
- 归因链条（Agent 特有优势）：对着 trace 问——检索没召回？工具选错/调用参数错？规划循环？还是模型能力不足？**归因到环节，才知道改哪**
- 评测护栏的真实价值：Voiceflow 的任务级评测护栏抓住了模型升级（gpt-3.5-turbo-0301→1106）带来的 **10% 静默回归**【单源：Eugene Yan】

**3.4 数据飞轮（4'）**
- 对照表（本节核心 slide）：

| | 传统 ML 飞轮 | Agent 飞轮 |
|---|---|---|
| 数据来源 | 标注样本、线上预测+回流标签 | trace 轨迹、显式/隐式反馈、任务成败信号 |
| 主要杠杆 | 重训模型（周/月级） | prompt / 工具定义 / 编排逻辑 / 换模型 / 微调（天级） |
| 门禁 | 离线指标+A/B | 评测集回归门禁 |
| 发布 | 金丝雀→A/B→回滚 | 同样适用 + rainbow deployment 平滑切流、checkpoint 恢复重试 |

- 标准发布流程（对 RAG/Agent 通用）：**离线评测门禁 → 金丝雀 → A/B → 全量+监控**【单源：StackAI】
- Anthropic 的 agent 专属运维：长任务有状态，用 rainbow deployment 让新旧版本同时服务逐步切流；出错从 checkpoint 恢复而非重启【单源·一手：Anthropic】
- **本节小结**：上线不是终点，是飞轮的起点。评测集是飞轮的轴承。

### 第 4 节 统一框架收束（5'）

- 一张图收束：同一条生命周期，两个时代的形态并排
- **什么没变**（四个不变）：数据质量决定上限；上线不是终点；评测是门禁；反馈闭环驱动迭代
- **什么变了**（四个变化）：迭代周期 月→天；迭代杠杆 重训→多杠杆；数据形态 标注样本→轨迹与反馈；交付单元 单模型→模型+检索+工具+流程的系统
- **小公司务实路线**（收尾赠言）：
  1. 先 workflow 后 agent（简单可组合模式起步）
  2. 评测集先行：20-50 条真实查询就能开始
  3. 直接调 API，别急着上框架（Anthropic 对数十个团队的观察）
  4. 先建监控，再谈优化——没有 trace 就没有归因，没有归因就没有飞轮
