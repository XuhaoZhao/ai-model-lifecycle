### S4｜答案：80% 在数据
**类型**：揭底页
**页面要点**：
- **80% 在数据**（巨型数字）：行业经验法则——数据准备约占项目 80%（data munging）
- 数据准备五个任务：选择 → 清洗 → 构建 → 整合 → 格式化；官方原话：**清洗「往往是最耗时的任务」**
- 建模，通常是最短的阶段
- LLM 呼应条：FineWeb 15T 原始网页 → 过滤出 1.3T 高质量子集，**同等训练预算**：MMLU 33→37 · ARC 46→57。附基准备注：MMLU 考 57 个学科的知识题、ARC 考小学科学推理题（不写前向页码引用）
**讲稿备注**：出处为 CRISP-DM 官方介绍【单源：datascience-pm.com】；可信度补强：KDnuggets 2002/2004/2007/2014 四次调查 CRISP-DM 使用率均第一【单源，同页】。FineWeb 数字【已验证：arXiv 2406.17557】。补一句：这不是新现象——1999 年的方法论就总结出了这条法则，LLM 时代依然成立（FineWeb 即证）。

### S7｜业界标准流程：Google 的 8 步
**类型**：内容页
**页面要点**：
1. 数据抽取　2. 数据分析　3. 数据准备（清洗/划分/特征）
4. 模型训练　5. 模型评估　6. 模型验证
7. 模型服务　8. 模型监控
- 这些步骤的**自动化程度** = MLOps 成熟度。澄清：它量的不是模型效果，是交付流程；效果够不够格上线由第 5 步评估指标 + 第 6 步验证（效果达标 + 预测服务工程标准）决定。**不写页码前向引用**
**讲稿备注**：来源 Google Cloud Architecture Center【已验证】。强调第 8 步：监控发现问题会「invoke a new iteration」，流程从终点绕回起点，这是「闭环」的第一次出现。结尾提示观众记住"自动化程度=成熟度"这句话，本节收尾（S18）用它给团队打分——**S18 开场必须回扣 S7 这句话**，不能默认观众还记得。

### S10｜特征的平台化：Uber 的 Feature Store
**类型**：案例页
**页面要点**：
- Uber Michelangelo（2016 年起）：集中式特征平台
- 约 **10,000 个特征**跨团队共享，每日自动计算更新

### S13｜上线不等于全量：三种验证策略
**类型**：内容页
**页面要点**：
- **影子部署**：新模型只记录预测、不生效
- **金丝雀**：小流量先吃异常
- **A/B 测试**：线上真实对照

**讲稿备注**：Evidently 把「生产 / 影子 / A-B」列为需要监控的三类场景【单源：Evidently】；CRISP-ML(Q) 把 A/B、canary/blue-green 与回退预案列为标准部署任务【单源：ml-ops.org】。一句话：**模型上线和代码上线一样，要有灰度思维**。

### S14｜上线之后：模型会「腐烂」
**类型**：内容页
**页面要点**：
- 模型性能下降，**不止因为代码缺陷，更因为数据分布在变**
- **数据漂移**：输入分布变了（X 变了）
- **概念漂移**：X 与 Y 的关系变了（可渐变、可突变）
- 例：风控模型 vs 新型欺诈手法
**讲稿备注**：Google 原文「ML models can decay in more ways than conventional software systems」【已验证】。两类漂移区分来自 Evidently【单源】。金句：传统软件不修就不会坏；**模型什么都不做也会坏**。

---

### S15｜线上故障的分类学与代理指标
**类型**：内容页
**页面要点**：
- 多数生产故障源于**数据质量/完整性**：管道断裂、上游 schema 变更、数据丢失
- 其他：训练-服务偏差、级联上游模型故障、弱势子段表现差
- 难题：**真实标签有延迟**（转化可能几天后才发生）
- 对策：代理指标预警——预测分布漂移、输入漂移、新类别占比
**讲稿备注**：【单源：Evidently】。讲清逻辑链：标签没回来 → 算不了线上准确率 → 先盯输入端和输出端的分布变化，作为「模型可能坏了」的早期烟雾报警器。

### S16｜闭环的落地长什么样：Michelangelo 的实现
**类型**：案例页
**页面要点**：
- 自动抽样记录线上预测 → 与回流的真实结果 **join** → 生成线上准确率时序（RMSE 等）→ 阈值告警
- 这就是「监控 → 反馈」两步的工程实现
**讲稿备注**：【单源·一手：Uber 2017】。点评：所谓反馈闭环，工程上朴素得很——预测日志和结果表 join 起来。难的不是技术，是**结果回流的数据管道**要先建好。

### S17｜闭环的本质：持续训练（CT）
**类型**：内容页
**页面要点**：
- MLOps = DevOps + ML 特有的三件事：
  - **CI** 不只测代码，还要测**数据、schema、模型**
  - **CD** 部署的是「训练流水线」，由流水线再去部署预测服务
  - **CT** 持续训练：自动重训 + 自动上线，ML 独有
**讲稿备注**：Google 的 CI/CD/CT 对比【已验证】。金句：传统软件部署的 artifact 是程序；ML 部署的 artifact 是**一条会不断生产模型的流水线**。

### S23｜三个有记忆点的数字
**类型**：内容页
**页面要点**：
- **15T**：Llama 3 预训练 token 数（Llama 2 是 1.8T）
- **50×**：405B 模型的训练算力（16K 张 H100）
- **1.3B > 175B**：对齐后的 1.3B InstructGPT，人类偏好度超过 175B 原始 GPT-3
**讲稿备注**：前两个来自 Llama 3 报告与 Meta 工程博客【单源·一手】；第三个来自 InstructGPT 论文【单源·一手：arXiv 2203.02155】——结论：**对齐的价值大于堆参数**。可补 Chinchilla：算力最优要求参数与数据同比例增长，此前多数模型「训练不足」【单源·一手：arXiv 2203.15556】。

### S25｜agent = 模型 + harness
**类型**：内容页
**页面要点**：
- Anthropic 定义：agent harness（scaffold）= 处理输入、编排工具调用、返回响应的系统；**评测一个 agent，评的是 harness 和模型协同工作的整体**；Claude Code 就是一个 harness
- harness 三块：上下文管理 / 工具调用循环 / 环境接口
- 为什么重要：换模型 ≠ 换 agent；调优对象常在 harness；编排、工具设计、多智能体全是 harness 层的事
**讲稿备注**：【单源·一手：Anthropic evals 工程文，逐字核对】。落点：底座是买的，harness 和编排是自己造的，小公司真正要做的一层。

### S26｜harness 工程（一）：上下文工程
**类型**：内容页
**页面要点**：
- Anthropic：猜谜式 prompt 工程 → 系统化的注意力管理
- 比值公式：注意力 / 干扰 = 信号 / 噪声（注意力是分子，干扰是分母）
- 三手段：压缩 compaction（历史折叠成摘要）· 结构化笔记（固定格式笔记区）· 子代理架构（小上下文回传浓缩结果，多智能体页回收）
**讲稿备注**：【单源·一手：Anthropic《Effective Context Engineering for AI Agents》2025-09-19】。比喻（管理内存）只在讲稿。

### S27｜harness 工程（二）：执行环境与安全边界
**类型**：内容页
**页面要点**：
- 沙箱执行：写操作圈在隔离环境，坏了只坏沙箱
- 权限与委托：每次调用校验身份 / 资源范围 / 有效期，高危操作单独审批，不发长期通行证
- 最小权限：默认最小范围，用完收回
- 起步建议：现成 harness（Claude Code / Agent SDK / 开源框架）+ 直接调 API，先跑通再自建
**讲稿备注**：安全边界为业界通行实践；架构趋势参考主讲人存档文章《别再给每个 Agent 塞一个 Sandbox》（从满地沙箱 → harness 层统一治理）。

### S28｜Agent：先分清两个词
**类型**：内容页
**页面要点**：
- **Workflow**：LLM+工具按**预定义代码路径**编排
- **Agent**：LLM **动态决定**自己的流程与工具使用
- 统称 agentic system；积木是「增强型 LLM」= LLM + 检索 + 工具 + 记忆
**讲稿备注**：Anthropic 官方区分【单源·一手】。金句：workflow 是你画流程图，agent 是它自己画流程图——自主性换来的能力与风险都更大。

### S29｜五种生产验证过的编排模式

**讲稿备注**：Anthropic 从数十个团队生产实践总结【单源·一手】。建议：按成本从上往下选，能 1 不用 2。

### S30｜ReAct：推理与行动交织
**类型**：内容页
**页面要点**：
- Thought → Action → Observation 循环
- 推理轨迹：制定/更新计划、处理异常
- 行动：调外部工具/知识源补信息
- 在 HotpotQA/FEVER 上缓解纯思维链的**幻觉与错误传播**
**讲稿备注**：ReAct 原论文【单源·一手：arXiv 2210.03629】。展示一段 3 步轨迹示例（口头描述即可）：模型发现信息不够 → 查工具 → 修正答案。轨迹可读 = 天然可归因，第 3 节回收这一点。

### S31｜工具接入的工业标准：MCP
**类型**：内容页
**页面要点**：
- Model Context Protocol：开放标准，**「AI 应用的 USB-C」**
- 解决 N×M 接入问题：模型 × 工具，每个都写一遍胶水代码 → 统一协议
- 架构：host → client（每 server 一个）→ server（本地 STDIO / 远程 Streamable HTTP）
- 三原语：**Tools**（可执行函数）/ **Resources**（上下文数据）/ **Prompts**（模板）
**讲稿备注**：MCP 官方文档【单源·一手：modelcontextprotocol.io】。类比展开：以前每个设备一个专用接口（N×M），USB-C 一个口通吃（N+M）。

### S32｜工具设计是新的接口设计（ACI）
**类型**：内容页
**页面要点**：
- Anthropic 造 SWE-bench agent：**花在工具定义上的精力 > prompt 本身**
- ACI（agent-computer interface）值得投入与 HCI（人机接口）同等的严谨
- 工具描述模糊 = agent 调用出错的最大来源之一
**讲稿备注**：【单源·一手：Anthropic Engineering】。给开发同学的具体启示：给 agent 写工具 API，要像给新人写 onboarding 文档一样写——名字、参数、返回、什么时候用、什么时候别用。

### S33｜多智能体：orchestrator-worker
**类型**：内容页
**页面要点**：
- 模式：主 agent 规划并持久化计划 → 派生 3-5 个并行子 agent → 汇总 + 引用
- 实测：内部研究评测**超过单 agent 90.2%**；复杂查询研究时间最多 **-90%**
- 收益来源：并行 + 上下文隔离（子 agent 各自小上下文，回传浓缩结果）
**讲稿备注**：Anthropic 多智能体研究系统【单源·一手】。强调与「传统静态分块检索」的对比是他们自己给的。

### S34｜多智能体的成本账（必讲）
**类型**：内容页
**页面要点**：
- token 用量单独解释了 **80%** 的性能方差
- 生产数据：agent ≈ 对话 **4×** token；多智能体 ≈ **15×**
- 结论：**多智能体只对高价值任务划算**
**讲稿备注**：【单源·一手：Anthropic】。翻译成预算语言：一次多智能体任务的直接成本是普通对话的十倍量级——先确认任务价值再上架构。

### S35｜Anthropic 的工程忠告
**类型**：内容页
**页面要点**：
- 最成功的实现用**简单、可组合的模式**，不是复杂框架
- 从**直接调 API** 起步，别急着上框架
- 自主 agent 上线前：**沙箱测试 + 护栏**（成本与误差会复利）
**讲稿备注**：来自 Anthropic 与数十个团队一年的合作观察【单源·一手】。这一页是给小公司的定心丸：业界头部也在做减法。

## 第 3 节 生产与持续迭代（S36-S47，15'）

### S36｜章节页：上线之后
**类型**：章节页
**页面要点**：
- 03 上线不是终点：监控、Bad Case 与数据飞轮

### S37｜推理服务的瓶颈：显存
**类型**：内容页
**页面要点**：
- KV cache 有多大：LLaMA-13B 单序列可达 **1.7GB**，且动态变化
- 传统推理系统因碎片化与过度预留，**浪费 60-80% 显存**
**讲稿备注**：vLLM 团队测量【单源·一手：vLLM 博客】。类比：像手动管理内存的 C 程序 vs 有 GC 的语言——LLM 推理长期在「手动管理」时代。

---

### S38｜vLLM：把操作系统分页搬进推理
**类型**：内容页
**页面要点**：
- PagedAttention：KV cache 按块分页、逻辑/物理块映射，浪费 **<4%**
- 吞吐：最高 **24×** HuggingFace Transformers、**3.5×** TGI
- 实战：LMSYS Chatbot Arena 用后 **GPU 减半**（日均 3 万请求，峰值 6 万）
**讲稿备注**：【单源·一手：vLLM】。一句话总结选型意义：**部署开源模型的默认起点**。
**配图**：左「连续预留（大量灰色浪费）」右「分页（紧凑）」显存布局对比图。

---

### S39｜推理加速组合拳
**类型**：内容页
**页面要点**：
- **量化**：精度换显存（FP8/INT8/INT4、GPTQ、AWQ…），格式与 GPU 代际强相关；KV cache 也可单独量化
- **投机解码**：小模型/草稿先猜、大模型验证；LinkedIn 实测——
  - n-gram 投机（无需草稿模型）+ vLLM：吞吐近 **4×**，P90 **-66%**，**输出无损**
  - 生效前提：生成内容与输入高度重叠（如基于 JD 的结构化分析）
**讲稿备注**：量化来自 vLLM 文档【单源·一手】；投机解码来自 LinkedIn Engineering【单源·一手】。方法论：**加速手段要匹配负载特征**，先看自己的生成模式再选。

---

### S40｜LLM 应用的监控：四个维度
**类型**：内容页
**页面要点**：
- 传统服务监控（可用性/延迟）之外，再加：**数据健康 + 模型健康**
- LLM 四维度：**质量**（幻觉率/用户反馈）· **成本**（token）· **延迟** · **trace**（轨迹）
- 工具现状：MLflow 内建 OpenTelemetry tracing、50+ 内置指标与 LLM judge、prompt 管理、AI Gateway 成本管理
**讲稿备注**：分层说法来自 Evidently【单源】；MLflow 能力【已验证：mlflow.org】。强调 trace 是 LLM 应用独有的第三层——没有 trace 就没有后面的归因。

---

### S41｜幻觉的现实与实时检测
**类型**：内容页
**页面要点**：
- 现实：做了知识接地 + 好 prompt 的生产系统，典型事实错误率仍约 **5-10%**；降到 2% 以下极难
- 生产实践（Datadog）：黑盒 LLM-as-judge **实时**检测幻觉
  - 自动分类：**与上下文矛盾** vs **无依据论断**
  - 敏感场景两类都拦，不敏感只拦「矛盾」
- 扰动式检测太贵（5-10× 调用成本），故选黑盒 judge
**讲稿备注**：5-10% 与 2% 来自 Eugene Yan【单源】；实时检测来自 Datadog【单源·一手】。给听众的预期管理：**别承诺零幻觉，设计兜底**。

---

### S42｜Bad Case 从哪来、怎么归因
**类型**：内容页
**页面要点**：
- 收集：显式（点赞点踩、人工接管）+ 隐式（重试、改写、放弃）
- **归因链条**（对着 trace 逐环排查）：
  检索没召回？→ 工具选错/参数错？→ 规划循环？→ 模型能力不足？
- 归因到环节 → 才知道改哪一环
**讲稿备注**：这是 Agent 相对传统 ML 的独特优势：轨迹把失败暴露在具体环节上（呼应 S28）。传统模型只有一个输出可看，agent 的每一步都可审计。

---

### S43｜评测集：不用大，但要真
**类型**：内容页
**页面要点**：
- Anthropic 多智能体系统：**从约 20 条真实查询起步**
- Anthropic evals 工程文（2026-01）：**20-50 个「来自真实失败」的简单任务就是很好的起点**；已上线团队从 bug 单与客服队列收集
- StackAI 建议：**50-200 条真实用户查询**做金标集
- 评测方法：单次 LLM-as-judge（0.0-1.0 分 + rubric 通过/失败）与人工判断最一致
- 但 judge 有局限：幻觉检测准确率仅 ~54-58%；**人工测试不可替代**（Anthropic 靠人工发现 agent 偏爱 SEO 内容农场）
**讲稿备注**：Anthropic【单源·一手】、StackAI【单源】、judge 局限来自 Eugene Yan 引 HaluEval 数据【单源】。金句：**评测集是团队最重要的资产之一，20 条今天就建得起来**。补充闭环：监控回流的坏案例是评测集最高价值的新增——"failures become test cases, test cases prevent regressions"；回归评测保持近 100% 通过率、专防倒退，能力评测高通过率后「毕业」为回归套件；评测集是"活物"，要与真实用法同步否则制造虚假信心【单源·一手：anthropic.com/engineering/demystifying-evals-for-ai-agents 2026-01】。

---

### S44｜评测护栏的真实价值
**类型**：案例页
**页面要点**：
- Voiceflow：模型升级 gpt-3.5-turbo-0301 → 1106，评测护栏抓住 **10% 静默回归**
- 专用检测器：几百条任务数据微调 NLI 模型，ROC-AUC **0.56 → 0.85**
- 没有 eval：你不会知道升级伤了哪里
**讲稿备注**：均来自 Eugene Yan【单源】。「静默回归」点题：LLM 应用升级模型/prompt 没有编译器帮你拦错误，eval 就是你的编译器。

### S45｜数据飞轮：传统 ML vs Agent（核心对照）
**类型**：表格页
**页面要点**：

| | 传统 ML 飞轮 | Agent 飞轮 |
|---|---|---|
| 数据来源 | 标注样本、线上预测+回流标签 | trace 轨迹、显式/隐式反馈、任务成败信号 |
| 主要杠杆 | 重训模型（周/月级） | prompt / 工具定义 / 编排 / 换模型 / 微调（天级） |
| 门禁 | 离线指标 + A/B | 评测集回归门禁 |
| 发布 | 金丝雀 → A/B → 回滚 | 同样适用 + rainbow 平滑切流、checkpoint 恢复 |

**讲稿备注**：核心洞察：**闭环没变，转速变了**——传统 ML 转一圈要重训模型（周/月），Agent 转一圈可能只是改一段 prompt（天）。杠杆越多，飞轮转得越快。补一条连接线：「数据来源」行的监控数据同时喂养两处——作为**燃料**进训练/杠杆，作为**门禁**进评测集（坏案例 → 回归用例，Anthropic：failures become test cases）。
**配图**：两个转速不同的飞轮对比图（左慢右快）。

### S46｜Agent 的发布流程
**类型**：内容页
**页面要点**：
- 通用流程：**离线评测门禁 → 金丝雀 → A/B → 全量 + 监控**
- Agent 特有：
  - **Rainbow deployment**：新旧版本同时服务、逐步切流（长任务不中断）
  - **Checkpoint 恢复**：出错从断点重试，而非整个重来
**讲稿备注**：发布流程来自 StackAI【单源】；rainbow 与 checkpoint 来自 Anthropic 多智能体实践【单源·一手】。对照 S13：灰度思维完全延续，只是 agent 有状态、任务长，切流方式更讲究。

### S49｜什么变了，什么没变
**类型**：内容页
**页面要点**：

**讲稿备注**：收束全场的主旨页：生命周期框架是稳定的，环节形态在演化——所以「生命周期视角」比任何单项技术都保值。
