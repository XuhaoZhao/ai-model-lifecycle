别再给每个 Agent 塞一个 Sandbox：下一代 Agent 架构

原文：微信公众号「人工智能前线」· 2026-09-30 · mp.weixin.qq.com · 全文存档：original-article.md · 文中产品 Tetral 已 MIT 开源
“一台计算机，应该是 Agent 调用的一种资源，而不是 Agent 所在的地方。”

真正需要扩展的不是 Sandbox，而是一个长期运行、可恢复、可跨设备、可独立调度资源的 Agent 系统 —— 作者称之为 The Next Scaling Problem。

旧架构：Agent 住在 Sandbox 里扩容 = 扩完整捆绑单元

  • 整个 Agent Loop + 会话历史 + Trace + 临时文件都留在 Sandbox 内
  • 排查问题要进入持有用户私有数据的环境
  • API Key 不敢放进 Sandbox，只好外挂 Gateway 打补丁
  • Runtime 一死，Agent 跟着死；容量被“能提供多少台计算机”限死
➜

新架构：Agent 在 Sandbox 外各部分独立扩缩

  • Runtime 只负责“计算下一步”，是可替换的计算宿主
  • 状态在 PostgreSQL、凭证在 Gateway、投递靠 Queue
  • Computer 按需分配（Lazy Allocation），只是资源之一
  • 执行可以失败、Runtime 可替换、Computer 可更换 —— 身份与历史不丢
图一

系统总体架构：Runtime 只保留“计算下一步”

所有具有不同生命周期、不同所有权、不同扩展模式的职责都被移出 Runtime，各自成为可独立扩容的服务；Runtime 变成无状态、可替换的计算宿主。

客户端 产品接口 状态与投递 计算 资源

客户端 —— Agent 是“可寻址的参与者”，以同一身份跨界面持续存在

Terminal浏览器手机 GitHubSlack · 团队产品 关闭客户端 ≠ 结束 Session；连续的是有序的 Session History

Public API

接收用户请求，不执行 Agent。接受请求 = 同一事务写入 Input + Inbox + Queue Job（Outbox）：可直接返回“已接受”，送达异步完成。

Event Stream

向外部客户端暴露状态更新。只是产品接口，不保存 Agent 会话状态，不执行 Agent。

PostgreSQL · 最终事实来源

用户输入 · 执行进度 · 工具结果 · 审核结果。Session Log = 完整逻辑执行记录（≠ 聊天记录）；另有 Context Projection 供模型加载。

Bridge · 状态边界与事务

Runtime 只声明“下一步想做什么”；Bridge 验证它是否仍拥有该 Session、检查执行顺序，再决定能否提交。

Queue · 可靠投递

顺序 · 租约 · 重试 · 取消 · 死信。数据库解决“存没存下”，Queue 解决“送没送到正确的执行者”。

Agent Runtime —— 只负责“计算下一步”

Reducer 纯函数（不碰库 · 不联网 · 不执行工具） Session / Thread 计算 Tool Gate 授权边界 Context Projection 子 Agent 协调

可替换的计算宿主（K8s Pod）：不持有状态、不持有明文凭证 —— Pod 消失，就在另一台 Pod 重载已提交事实，继续计算（Durable Agent Work）。

Gateway · 模型接入（凭证终点）

统一 Provider 协议；API Key / OAuth 只到这里，刷新也在这里；先验证 Runtime 的 K8s 身份与 Session 所有权，再注入凭证。

Sandbox Service · Computer 生命周期

复用 / 启动 / 创建 / 替换 / 注入状态；多个等待者可共享同一次冷启动激活。执行 Shell 与文件系统操作。

Daytona VM（当前实现）轻量容器虚拟文件系统Linux / macOS / Windows

MCP Connector · 工具接入

Runtime 只见工具名 / 描述 / 输入 Schema，看不到 Server 凭证；Connector 验证权限、注入凭证、执行请求，结果先经 Bridge 再进上下文。

事件推送 ① Outbox：同一事务写入 Input · Inbox · Queue Job 投递任务 恢复：重放已提交事实 ② 先记录，再执行（声明带稳定 ID ＝ 幂等键） ③ 模型请求（不含任何凭证） ④ 声明需要 Computer 工具调用（声明）
①保存 ≠ 已送达：消息接受与 Queue Job 同事务落库（Outbox），通知丢失也能靠轮询发现。
②先记录，再执行（类 WAL）：任何推进状态或制造副作用的动作先经 Bridge 提交，再真正执行。
③凭证边界：明文凭证只存在于 Gateway / Connector，不进入 Runtime、Bridge、Session Log、Sandbox。
④Lazy Allocation：Computer 在首次真正需要时才分配，可复用则复用，不再是每个会话的默认配置。
图二

扩展的两个维度：Workspace / Session / Thread

Thread 用来扩同一个任务里的并行路径；Session 用来扩不同任务；Workspace 让不同 Session 共享长期资源。同一条 Thread 严格有序，不同执行路径尽可能并行。

Workspace —— 长期资源空间
文件 · Memory · 代码仓库 · 凭证 · Agent Version（生命周期最长，跨 Session 共享）
Session A：代码实现
Agent Version · 资源配置 · 历史 · 生命周期
Root Thread➜ Child Thread（实现） Child Thread（对抗式评审）
Session B：安全审计
不同的根 Agent · 上下文 · 凭证 · 生命周期
Root Thread➜ Child Thread
Thread 内严格有序后到的消息不能“超车”正在重试的投递，否则同一上下文顺序错乱；中断作为特殊消息，不被普通消息堵住。
Subagent 也是持久化实体Spawn 是一个事务：创建 Child Thread、父子关系、Inbox、Delivery Job 同事务提交；重试同一 Spawn 返回同一个 Child Thread，绝不重复创建。
父子上下文独立Parent 新消息不自动进入 Child，Child 不能直接改 Parent 上下文；所有通信都重新经过有序投递。
图三

一次高风险工具调用的完整路径

授权（这一次操作可不可以执行）与权限隔离（有没有资格用这个能力）是两回事；授权决策必须发生在 Agent 之外、执行之前。

1
提案模型提出 Tool Call —— 此时它只是一个“提案”，还不是可执行的调用。
2
Tool Gate（第一次）按 Session 的 Approval Mode、Tool Catalog、该类工具的 Policy，判断是否必须经过独立审核。
3
Reviewer（独立 Thread）看到待执行动作、上下文、主 Agent 输出、同轮其他 Tool Call、实际 Policy —— 这些只是“证据”，不是指令（文件 / 网页 / Tool Result 都可能携带 Prompt Injection）。返回：风险等级 · 允许或拒绝 · 原因；输出格式异常 = 审核失败，而非默认允许。
4
落库审核判断先经 Bridge 写入 PostgreSQL —— 记录成功才有效。
5
Tool Gate（第二次）拿到已提交的审核结果后再决定：允许 / 拒绝 / 升级到用户审批。
6
执行Tool Use 正式提交 → 进入 Queue → 由 Sandbox Service / MCP Connector 执行。
7
回收结果先经 Bridge 落库，再进入 Agent Context —— 执行环境可以消失，产出必须留下。
“审核结果本身不是权限；被系统正式记录并重新验证后的结果，才是权限。”

保守边界：若 Runtime 在“提案已产生、授权尚未完成”之间崩溃，恢复后提案不会自动继续执行 —— 宁可牺牲这一步的恢复能力，也不让失去上下文的孤儿授权继续生效。

附

六个关键原则

先记录，再执行

任何推进状态或制造副作用的动作，先提交声明、后真正执行（类 WAL）。声明带稳定 ID，即幂等键：重试返回已存结果；同 ID 不同内容直接拒绝。

凭证边界

明文凭证只存在于 Gateway / Connector。“能使用某能力”≠“持有密钥”；Credential Isolation 解决资格，Authorization 解决这一次动作可不可以。

Computer 是资源，不是住所

Lazy Allocation：首次需要才分配，能复用就复用。执行环境可以消失，产出必须留下 —— 代码与 Artifact 回到仓库和对象存储。

共享 Accepted Artifact

聊天只协调工作；只有经过对抗式评审 + 人审核接纳的 Artifact，才改变所有 Agent 共同信任的事实 —— 像只有 review 过的 commit 才进主干。

扩展瓶颈会不断外移

模型越强、跑得越久，压力依次落在身份、授权、历史、工具、存储、执行环境，甚至编译与测试工具链（Bun 转 Rust、TS 原生 Go 提速约 10 倍）。最短板即新瓶颈。

三个不变的下注

① Agent 是 Cloud Native 的；② 需要扩展的是整个 Agent System，而不只是模型；③ Runtime 只管计算下一步，外围系统负责连续性与控制（你是谁 / 做到哪 / 能访问什么 / 是否被允许）。
